# Existing-draft RLS probe

`blog_rls_authorization.sql` is a manual, transaction-contained regression test. It has **not** been run by this repository. Prefer an isolated Supabase/Postgres project with the blog migration applied, one allowlisted Auth admin and a distinct authenticated non-admin. Do not run it against the live `exo-portfolio` database without explicit owner authorization.

1. In the intended project's SQL Editor, confirm the project reference and that the non-admin and admin Auth users exist. Copy the script into the editor and replace `<ADMIN_AUTH_UUID>` and `<NON_ADMIN_AUTH_UUID>` with their respective user IDs **in the editor only**. Never commit the filled-in script, paste JWTs or service-role keys, or share unredacted query output.
2. Run the **entire** script as one batch in the same SQL session. The editor's privileged role only creates and verifies a unique draft fixture. The authorization assertions switch to PostgreSQL role `authenticated`, set both `request.jwt.claim.sub` and `request.jwt.claims`, verify `auth.uid()`, verify the role does not bypass RLS or own the table, and check that table-level grants exist. A zero-row UPDATE/DELETE can therefore not pass because the fixture was absent or basic table grants were missing.
3. Expect these `PASS` notices: fixture confirmed; non-admin SELECT denied; non-admin UPDATE existing draft denied; non-admin DELETE existing draft denied; non-admin INSERT rejected **by RLS**; admin SELECT allowed; fixture unchanged before rollback; temporary data cleanup verified. The script ends with `ROLLBACK`, then checks that its exact draft UUID is absent. No actual credentials or tokens are needed in SQL.
4. If any assertion fails or execution stops early, issue `ROLLBACK` in the **same session** before doing anything else. Do not `COMMIT`. The initial `set_config` result contains the generated probe UUID (not a user ID); if needed, use that UUID to verify `SELECT count(*) FROM public.blog_posts WHERE id = '<PROBE_UUID>'::uuid` returns zero after rollback. Treat any failure, missing notice, or unverified cleanup as **HOLD** and investigate before retrying.

The SQL Editor's setup/cleanup privileges are **not** evidence of RLS enforcement. Only the checks while `current_user = 'authenticated'` with verified JWT claims count toward the authorization result. Record the outcome separately for SELECT, INSERT, UPDATE, DELETE, admin SELECT and cleanup. A local parse or code review is not a live Supabase authorization test.
